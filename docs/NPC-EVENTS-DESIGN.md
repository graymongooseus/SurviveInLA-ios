# NPC、关系与阶段事件

状态：完整 NPC 关系玩法的扩展规格。已接入 [FF 投资](FF-INVESTMENT-EVENT.md) 与 [陈冠希合影](CHEN-SANTA-MONICA-EVENT.md)，并有统一名人名册、个人限时增益和合照相册；下文的通用关系系统尚未接入运行时。本文的字段与目录是设计约定，不是当前 JSON 加载器已支持的格式。

## 已确认的玩法

游戏可以增加多位 NPC。在不同阶段，玩家运气与玩家和该 NPC 的关系共同影响其提供“协助”增益或造成“困扰”减益的事件。多个事件和持续效果可以共存，事件通过弹窗展示，各来源的效果参与叠加。

关系属于具体人物。玩家与甲关系好，不代表与乙关系也好；同一个 NPC 在不同阶段可以有不同的候选事件。收益倾向与效果强度仍由策划标注，不根据标题、关系名称或玩家财富自动推断。

## 内容、关系状态与效果实例分开

| 对象 | 保存内容 | 放在哪里 |
|---|---|---|
| NPC 定义 | 稳定 ID、名称文本 Key、介绍文本 Key、立绘引用 | 独立 NPC 内容文件 |
| NPC 事件定义 | 来源 NPC、阶段条件、收益评级、抽取权重、选项与效果引用 | 独立 NPC 事件文件 |
| 玩家与 NPC 的关系 | 是否认识、当前关系值、已经发生的关键选择 | 当前旅程存档，按 NPC ID 查询 |
| 持续效果定义 | 影响哪个统计项、修正数值、持续与叠加规则 | 各类事件共用的效果定义 |
| 持续效果实例 | 实例 ID、定义 ID、来源事件和 NPC、起止时间、冻结数值 | 当前旅程存档中的活动实例集合 |

关系初版建议使用一个有上下界的数值，例如 −100～100，0 为中立。这个范围是建议，尚未固定游戏平衡。是否认识独立记录，不能把“不认识”自动当成“已经认识且关系中立”。暂不增加信任、好感、恐惧等多条数值；只有具体玩法需要时再扩展。

当前名人内容使用 `characters/celebrities.json` 与 `events/celebrities/`，由 manifest 明确登记并保持稳定加载顺序。其他普通 NPC 的组织方式待其具体玩法确定。新增一个使用现有机制的 NPC 应主要添加人物、事件、文案和图片，不在 `GameEngine` 中新增人物姓名分支。

## 阶段、关系和运气怎样配合

```text
进入新一周 / 完成一次相关事件选择
    → 读取当前阶段条件与 NPC 关系
    → 过滤不满足条件、冷却中或已完成的事件
    → 基础权重 × 运气因子 × 对该 NPC 的关系因子
    → 使用游戏的种子随机数抽取
    → 记录结果；有选择时保存待选实例
    → 结算关系变化与效果，保存活动实例
    → 将事件通知加入展示队列
```

“运气 + 关系”表示两者共同影响概率，不应直接把两种不同量纲的原始数值相加。两项影响的强弱分别配置：提高关系倾向于增加该 NPC 协助事件的权重、降低困扰事件的权重；运气继续按照收益倾向与强度调整权重。关系对混合事件的作用需要明确配置，不凭混合效果猜测。

阶段条件先复用周数、已选选项、资产、装备和活动事件等现有条件。NPC 情节不占用目前“每个人生阶段只选一个人生事件”的名额，否则甲的故事会错误地阻止乙的故事。需要独立故事进度时，按 NPC 或故事线保存，而不是使用全局唯一的 NPC 阶段。

条件和权重预览不消耗随机数。关系不佳不必绝对禁止帮助，高运气也不保证一定获助；必须满足的故事前提写入条件，概率偏向写入权重。只有设计明确要求时才使用“关系至少达到某值”的硬门槛。

示例仅用于说明结构：已认识的房东在安顿阶段可能提供临时房租优惠，也可能增加催租压力；哪些事件符合条件，由阶段、租住状态和历史选择决定，再由关系与运气改变候选权重。具体人物、事件数值和文案不在本轮擅自定稿。

## 复用现有代码的位置

| 当前模块 | NPC 扩展点 |
|---|---|
| `EventContentCatalog` | 加载 NPC 与 NPC 事件；校验人物、文本、素材和效果引用 |
| `GameSession` | 保存按 NPC ID 区分的相识与关系状态，以及故事实例 |
| `EventCondition` | 增加是否认识某人、与某人关系比较；继续使用 AND／OR／NOT |
| `EventSelection` | 复用稳定候选顺序与加权抽取；NPC 权重增加关系因子 |
| `EventEffectExecutor` | 增加认识人物、关系变化和施加持续效果等明确的效果类型 |
| 持续效果结算 | 将世界与 NPC 的有效修正送入同一统计项计算流程，保留来源 |
| `GameStore` 与弹窗 | 保存并依次展示事件；显示人物、关系变化、效果来源和剩余时间 |

NPC 不伪装成世界事件，也不与世界池争夺同一次抽取。触发入口可以独立调度，条件、抽取、效果与校验共用。现有世界倍率函数尚不能代表全部个人增益机制，接入 NPC 时需要正式扩展持续效果模型。

每次实际获得效果都应能区分来源事件与实例。弹窗确认不是效果实例的身份；重复点击或读档不能重复结算。效果到期后从活动来源重新计算统计项，不通过反向加减或除法撤销。

## 尚待确定的细节

- 同一统计项的百分比相加还是倍率相乘，以及同种持续增益再次获得时的叠层、刷新或延长规则，沿用当前待答问题统一确定；NPC 不另设一套算法。
- 关系先只通过事件选项变化，还是同时需要聊天、送礼、求助等主动互动。前者可以先复用事件选择入口；后者需要额外动作入口、消耗规则和界面。
- NPC 每周或每阶段的触发数量、冷却与具体人物内容，在实际接入时通过策划配置确定。多事件共存不等于每周必须让所有 NPC 都触发一次。

## 接入时的兼容与验证

旧存档缺少 NPC 状态时按“尚未认识”读取，不补造历史关系；新人物不会自动插入已经结束的故事。已发布人物和效果的 ID 保持稳定，下架仍须兼容旧实例。

测试应覆盖：同种子下运气与关系分别改变抽取倾向；甲的关系不影响乙；未认识人物不进入要求相识的候选；不同 NPC 故事不错误互斥；同属性的世界与 NPC 修正共同生效并分别到期；读档恢复待选故事和未读通知且不重复改变关系或施加效果。
