# 系统架构

## 原则

首要目标是让游戏规则不依赖界面。SwiftUI 可以反复重做，数值结算和存档格式仍然稳定、可测试。

```text
SwiftUI Views
     │ 用户意图
     ▼
GameStore (@Observable, MainActor)
     │ 调用规则 / 发布状态
     ▼
GameEngine (纯 Swift、确定性随机数)
     │ 读写
     ▼
GameSession + GameContent + GameBalance
```

## 分层职责

| 层 | 当前职责 | 后续扩展 |
|---|---|---|
| App | App 生命周期和根页面 | 场景恢复、通知入口 |
| UI | 地图、状态、市场、交易弹层 | 背包、银行、日记、结局 |
| Store | 把点击转换为游戏动作 | 导航、存档、音效和触感协调 |
| Engine | 买卖、移动、利息、市场、事件 | 房租、贷款、技能、任务、结局评分 |
| Domain | 状态、商品、区域、事件、平衡参数 | Codable 存档与内容版本迁移 |
| Data | 三槽 JSON 自动存档、原子写入、随机状态恢复 | 存档版本迁移、JSON 内容包 |

## 状态边界

- `GameSession` 是一局游戏的唯一真实状态。
- `GameEngine` 只处理规则，不导入 SwiftUI、MapKit UI 或持久化框架。
- `GameStore` 只负责界面状态和错误提示，不复制经济计算。
- 随机数使用种子生成器；同一种子可重放同一局，方便测试和定位平衡问题。
- 商品、地点、事件最终迁移到版本化 JSON；程序代码只负责解释规则。

## 存档数据流

1. App 启动后读取三个 Profile 槽的最新 JSON 快照。
2. View 向 `GameStore` 发送买入、卖出或移动意图。
3. Store 调用 Engine；Engine 原子化修改 `GameSession`。
4. Store 在每次成功操作后原子覆盖当前槽的唯一快照，同时记录随机数状态。
5. 每次跨天记录结构化日志，以支持日记、重放和调试。

每个 Profile 只保留最新快照，不提供历史版本、手动读档或回滚入口。App 进入后台时会再保存一次，防止系统终止进程前遗漏界面状态。

## 不在首版引入

- 服务端、账号系统和实时多人游戏
- 第三方状态管理框架
- 远程配置和复杂依赖注入
- 为未来功能预先建立插件系统

排行榜和云存档只有在单机循环验证好玩之后才值得增加。
