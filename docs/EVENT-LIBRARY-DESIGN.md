# 洛杉矶浮生记：事件库与持续效果设计

状态：设计提案与分阶段实施记录。原提案基于 2026-09-05 工作区代码；示例数值用于说明结构，不代表已确定的游戏平衡。

目标：以后增加一个使用既有规则的新事件，只需添加内容和素材；只有出现一种全新的机制时，才扩展 Swift 引擎。

## 2026-09-06：已确认方向与实施进度

用户已明确：世界事件也组成事件库，运气越高越容易抽到高增益事件，运气越低越容易抽到负面事件。因此本轮目标将改变原提案中世界事件的既有抽取方式；下文有关保留旧世界排期和概率的内容仅作为迁移前行为参考，不再代表最终目标。

已进一步确认：世界事件由策划标注收益倾向与强度；按固定周期间隔抽取，允许多个世界事件重叠。周期初值为第 5 周起每 4 周一次，全部可在 manifest 中调整。

NPC 方向已确认：在不同阶段，由玩家运气和与具体 NPC 的关系共同影响“协助”增益或“困扰”减益事件。人物定义、玩家关系与效果实例分别管理；详细扩展规格见 [NPC、关系与阶段事件](NPC-EVENTS-DESIGN.md)。NPC 运行时和互动界面尚未实现，不能仅凭现有世界事件支持叠加就声称已具备人物关系玩法。

补充确认：多个事件与增益可以同时存在，事件通过弹窗展示，各种增益均参与叠加。界面采用逐个展示的通知队列；持续效果按活动实例结算，不能因等待弹窗、关闭弹窗或其他事件出现而被覆盖。当前世界事件实现已支持不同来源的同类数值修正共同生效，每个活动事件独立到期。

仍需区分两个数值设计细节：同一统计项的百分比采用相加还是倍率相乘，以及同一种持续增益重复获得时的层数与到期方式。当前代码使用倍率相乘，并排除仍在生效的同一世界事件；这两点是当前实现规则，不能把它们当成用户已确认的通用增益规则。下文早期 `refresh` 示例也不代表最终选定的重复获得策略。

已完成事件模型与效果执行器拆分，75 条事件迁入版本化 JSON 和独立文本；接入通用条件、策划收益评级、运气权重、可重叠世界事件和未读通知存档。既有 `GameEvent` 通过适配维持旧存档兼容。实际可用格式和剩余边界以 [事件库开发指南](EVENT-CONTENT-AUTHORING.md) 为准，下文保留早期完整规划供参考。

重构前基线：95 项测试，1 项跳过，0 失败；另保存 24 个种子、1,224 个行动检查点，用于核对数值与随机状态。新世界抽取规则落地时，需要单独记录预期变化，不能要求新玩法与旧玩法的事件序列相同。

本轮验证结果：109 项测试，1 项跳过，0 失败；新增 14 项事件库测试覆盖权重、周期、重叠、条件、效果、内容解析和存档恢复。75 条事件、222 处文本引用通过构建校验。纯代码抽取阶段的 1,224 个检查点与旧实现完全一致；切换世界抽取政策后，完整旅程运行通过，地点事件与人生选择的数据迁移保持一致，世界事件保留原文案、插图、持续时间和修正数值。

本轮后续已加入 [贾跃亭邀请投资 FF](FF-INVESTMENT-EVENT.md)：罗兰岗限定、玩家自选金额、10 回合延迟结算、存档恢复和独立通知队列。内容增至 76 条事件、232 处文本引用，快照升级 v4。验证为 121 项测试、1 项跳过、0 失败；完整 NPC 关系玩法仍按上方规格推进。

## 1. 先学清楚：钢铁雄心 4 值得借鉴什么

用户提供的 [data-driven-events-locations-localization.md](</Users/gongmingliu/Documents/Paradox Interactive/Hearts of Iron IV/docs/data-driven-events-locations-localization.md>) 是通用设计参考，其 YAML 是示意格式，并不是 HOI4 的原生事件脚本，也不是要求本项目逐条执行的开发指令。

HOI4 常见的相关内容目录可以这样阅读。这是理解职责的简图，不是本机安装版本的完整文件清单：

```text
events/                       事件定义、选项与事件内效果
common/on_actions/            在特定游戏动作发生时执行内容
common/scripted_triggers/     可复用的条件组合
common/scripted_effects/      可复用的效果组合
common/ideas/                 包含国家精神等持续修正的定义
common/dynamic_modifiers/     动态修正定义
history/states/               州的历史/初始设置
localisation/                 本地化文本
interface/                    包括图片资源的名称映射
gfx/                          图片等资源
```

应分别问：**在哪里定义内容、谁调用它、条件判断谁、效果修改谁、持续多久、如何显示？** 看一个事件文件时，还要沿着它引用的条件、效果、修正、文本和图片继续读。

Paradox 在官方 [Development Diary 52 — Modding](https://store.steampowered.com/news/posts/?appids=394360&enddate=1461329442) 中解释了共享条件/效果和事件目标：重复规则可以提取后复用，目标用于把效果施加到正确对象。对本项目的启发是“共享规则 + 明确目标”，而不是复制其完整脚本语言。

官方 [2024 年 Performance and Modding 开发日志](https://store.steampowered.com/news/posts/?appids=394360&enddate=1731420014&feed=steam_community_announcements) 还展示了从脚本向本地化文本传入变量的方式。我们可以借鉴这种文本与运行时数据的分工，继续使用适合 Swift 的内容格式。

| 概念 | 用洛杉矶的故事理解 | 建议承载方式 |
|---|---|---|
| Event 事件 | 后厨受伤，弹出两个选择 | `EventDefinition` |
| Hook 触发时机 | 一次后厨工作完成之后 | 引擎发出的动作上下文 |
| Trigger 条件 | 第 8 周以后、做的是后厨工作、尚未受伤 | `Condition` |
| Effect 一次性效果 | 健康减少 6、支付 80、得到工具 | `Effect` |
| Modifier 持续修正 | 未来 3 周打工收入减少 15% | `ModifierDefinition` |
| Fact 事实 | 曾选择带伤上工 | 存档中的类型化事实 |
| Scope/Target 对象 | 玩家、事发地点、这一次工作 | `EventContext` 的明确引用 |
| Localisation 文本 | 标题、故事、选项、不可选原因 | 文本 Key 与语言文件 |

事件是“发生了一次什么”，持续修正是“之后一段时间，规则怎样改变”。事件可结束，而修正继续存在；同一种修正也可以由多个事件产生。

## 3. 推荐文件组织：规则按职责分，故事按主题放

运行时内容采用版本化 JSON。理由是项目已使用 Codable 和 JSON 存档，没有必要为了配置文件引入新的解释语言。JSON 较啰嗦、不支持注释；用 `authorNote` 等编辑字段和编辑器模板补足。以后确实需要 YAML 作者文件时，在构建阶段转成同一份 JSON，不能维护两份可手工修改的权威内容。

以下是早期目标结构示意；实际落地目录与工具以本文开头链接的开发指南为准：

拆分标准是“一条故事链或一组紧密关联的短事件”，不是一个国家一大文件，也不是每个字段一小文件。市场、健康、钱财作为标签用于筛选；一条事件可以同时影响健康和收入，无须复制到两个目录。属于多个地点的事件只保存一次，用地点 ID 列表或标签表达范围。

内容文件是唯一来源，策划总表由它生成。表格展示：ID、标题、主题、地点、触发时机、条件、抽取规则、选项、效果、持续修正、后续事件和素材完成度。这样可以发现“某地点只有坏事件”等覆盖问题，又不会出现文档和代码两套数值。

作者的日常流程是：复制主题模板 → 写事件与中文文本 → 引用既有规则和素材 → 校验 → 用指定状态预览选项和结果 → 导出总表并审查差异。新增一个复用现有修正的普通事件，通常只需改事件文件、对应语言文件和内容清单；新增修正时再增加修正定义。只有词表不能表达新机制时，才修改引擎。

`manifest.json` 记录格式版本、内容版本和显式文件清单；加载器按约定顺序加载、跨文件校验后建立目录索引。编辑期辅助字段可以随加载剔除。Swift 的 Codable 解码成功不等于内容已通过验证，未知 Key 检查、重复检测和引用检查需由校验器补充。

现阶段本地 JSON、Swift 字典索引和 Git 足够。只有出现大量非程序作者同时编辑的实际需求时，再考虑可视化编辑器或数据库后台。

## 4. ID、定义、实例、结果要分开

新内容使用语义 ID，例如 `event.work.kitchen_injury`、`modifier.health.hand_injury`。事件内选项用 `rest`、`continue_working`，完整地址为 `(eventID, optionID)`，不依赖排列顺序。

现有 `san-gabriel-kitchen-burn` 等 ID 保留；不为了命名整齐批量重命名。人生选项迁移时把旧的 `landing-wallet-0` 显式映射到语义选项，历史文本保留原样。已有存档缺少的选择细节不能靠猜测补全。

| 数据 | 例子 | 放在哪里 |
|---|---|---|
| 定义 | 后厨受伤有哪些选项、修正数值 | App 内容包 |
| 实例 | 本局第 10 周、圣盖博、某次工作引发的受伤 | `GameSession` |
| 结果 | 选择休养，实际扣 80 美元、健康实际减少 6 | 结算记录/日记 |

`EventInstance` 至少记录实例 ID、定义 ID/版本、来源动作 ID、发生周、绑定目标、待选/已结算状态。发生时需要抽取的随机参数只抽一次并保存。`ResolvedEvent` 记录选择和实际变化；内容里的 −6 健康经过世界修正和 0～100 上下限后，实际可能不是 −6。

同一事件定义可以反复发生，不能把定义 ID 当成“这一次点击是否已结算”的凭证。用实例 ID 防重复结算，用定义 ID 加目标范围控制一次性和冷却。

## 5. 条件复杂之后，仍然能读懂

条件是只读表达式，只返回通过/失败及原因。不能扣钱、抽随机数、写标记或改变冷却。界面预览和实际点击都调用同一个条件判断器。

最初支持以下有限词表即可：

| 类别 | 示例 |
|---|---|
| 布尔组合 | `all`、`any`、`not` |
| 数值 | 周次范围、现金 ≥ 80、健康 < 40、运气 ≥ 60 |
| 身份与生活状态 | 有住房、有可用驾照、有车辆、有工具 |
| 动作上下文 | 本次工作带 `kitchen` 标签、目的地为圣盖博 |
| 内容状态 | 有某修正、某事实为真、某选择已完成 |
| 复用 | 引用一个命名条件 |

例如“有车辆，而且驾照当前有效，而且没有受伤”可组合为 `all`。有车和有驾照不是一回事；条件应复用 `hasActiveDriversLicense(in:)` 的含义，包括暂停/恢复周次，不能只读一个布尔值。

复杂规则也需要清楚的目标：`player`、`originDistrict`、`destinationDistrict`、`job`、`commodity`。先实现本项目实际使用的对象；没有 NPC 关系系统时，不为它提前建立角色作用域解释器。

JSON 中的 `field`、`op`、`target` 必须被解析为 Swift 枚举和明确处理函数，不能用任意字符串反射访问 `GameSession`，也不用 `eval` 执行公式。未知字段、未知操作、错误对象类型在加载时拒绝。

只被一个事件使用的条件留在事件中；多处重复且业务含义相同，再提取到 `triggers/`。共享条件循环引用应在加载时检查。

## 6. 一个贯穿例子：后厨受伤

下面是拟议 JSON 格式的完整事件示例。`kitchen` 是需要补入工作目录的标签；`pool.work_incident` 及所引用的修正也需要定义。这些字段目前不能直接由游戏加载。

故事：第 8 周以后，一次后厨工作结束时可能划伤手。支付休养成本可减少后续损失；现金不足也始终能选择硬撑，但会在未来几周承受工作惩罚。

```json
{
  "id": "event.work.kitchen_injury",
  "revision": 1,
  "tags": ["work", "health"],
  "presentation": {
    "titleKey": "event.work.kitchen_injury.title",
    "bodyKey": "event.work.kitchen_injury.body",
    "imageAsset": "Event_san-gabriel-kitchen-burn"
  },
  "activation": {
    "hook": "after_work",
    "poolId": "pool.work_incident",
    "weight": 10,
    "when": {
      "all": [
        {"op": "compare", "field": "week", "cmp": "gte", "value": 8},
        {"op": "has_tag", "target": "job", "tag": "kitchen"},
        {"not": {"op": "has_modifier", "target": "player", "id": "modifier.health.hand_injury"}},
        {"not": {"op": "has_modifier", "target": "player", "id": "modifier.health.recovering_hand"}}
      ]
    }
  },
  "repeat": {"mode": "cooldown", "weeks": 8, "scope": "player"},
  "resolution": "choice",
  "options": [
    {
      "id": "rest",
      "textKey": "event.work.kitchen_injury.option.rest",
      "costs": [{"resource": "cash", "amount": 80}],
      "effects": [
        {"op": "change_health", "amount": -6},
        {"op": "add_modifier", "target": "player", "id": "modifier.health.recovering_hand", "durationWeeks": 2}
      ]
    },
    {
      "id": "continue_working",
      "textKey": "event.work.kitchen_injury.option.continue_working",
      "costs": [],
      "effects": [
        {"op": "change_health", "amount": -6},
        {"op": "set_fact", "id": "fact.work.worked_while_injured", "value": true},
        {"op": "add_modifier", "target": "player", "id": "modifier.health.hand_injury", "durationWeeks": 3}
      ]
    }
  ]
}
```

这里两条选项都包含初始伤害，是有意把整个选择结算为一次事务。若以后需要“弹窗出现前已经受伤”，再引入有明确结算记录的 `onActivate` 阶段，不能在显示弹窗时暗中执行。

`costs` 会自动产生可用性判断和“需要现金 $80”的提示；现金不足时 `rest` 不能选择。一次性损失不是支付能力：现有罚款可能把现金扣到零，不能把它自动转换成“余额不足则免罚”。引擎分别支持主动支付和有明确不足处理规则的被动损失。

示例复用已有伤害插画只为展示资产引用；正式新增内容是否适合共用，仍按故事审查。

对应的中文文本：

```json
{
  "event.work.kitchen_injury.title": "后厨受伤",
  "event.work.kitchen_injury.body": "在{districtName}收工前，你划伤了手。下周的排班还没有定下来。",
  "event.work.kitchen_injury.option.rest": "花点钱处理伤口，减少接活",
  "event.work.kitchen_injury.option.continue_working": "包扎一下，继续接活"
}
```

价格和效果提示由规则数据生成，故事文案避免另写一套 −15% 和持续周数。中文为回退语言；开发环境缺 Key 显示 Key 并报错。各语言占位符必须匹配。

## 7. 增益与减益：共用一套持续修正

`modifiers/health.json` 中可有如下定义：

```json
[
  {
    "id": "modifier.health.hand_injury",
    "nameKey": "modifier.health.hand_injury.name",
    "stacking": {"mode": "refresh", "scope": "target"},
    "rules": [
      {"stat": "work.net_income", "operation": "multiply", "value": 0.85},
      {"stat": "work.health_cost", "operation": "add", "value": 2}
    ]
  },
  {
    "id": "modifier.health.recovering_hand",
    "nameKey": "modifier.health.recovering_hand.name",
    "stacking": {"mode": "refresh", "scope": "target"},
    "rules": [
      {"stat": "work.net_income", "operation": "multiply", "value": 0.95}
    ]
  }
]
```

`modifier.health.hand_injury.name` 的中文为“手伤未愈”；`modifier.health.recovering_hand.name` 为“手伤休养”。持续时间由施加效果给出，同一种手伤可以有不同持续时间。定义本身不记录某个玩家何时受伤。

活动实例保存：`instanceID`、`definitionID/revision`、`sourceEventInstanceID`、目标、`startsAtWeek`、`expiresAtWeekExclusive`、层数，以及需要冻结的强度参数。

必须先固定以下语义：

- 持续 3 周且在第 10 周激活，生效区间是 `[10, 13)`，第 13 周开始过期。本次工作已经结算，所以不会追溯扣减这一份工资；如果想保证之后能覆盖 3 次工作，应使用另一种“剩余次数”机制，不能把次数叫作周数。
- 同一种修正重复获得：`refresh` 更新到期周为 `max(原到期周, 本次开始周 + 持续周数)`；其他策略可逐步加入 `ignore`、`replace`、`stack(maxStacks)`。不能靠文件加载顺序决定。
- 不同修正可以同时存在。若未来设计互斥状态，再增加明确的互斥组与替换规则。
- 过期时移除规则，从基础值重新计算；不能乘 0.85 后，再在过期时除以 0.85，也不能擅自返还事件造成的健康损失。
- 装备加成由当前装备状态派生，事件修正由活动实例提供，最后进入同一个计算器。卖车或失去工具时不应留下永久加成副本。

数值应分计算阶段。比如：

```text
基础工资
  → 工具对基础工资的加成（沿用现有取整）
  → 加小费/扣款、减运营成本
  → 净收入修正：世界事件、手伤等
  → 按该阶段规则取整，得到入账值
```

同一阶段推荐统一为 `clamp((base + Σ固定值) × Π倍率, 下限, 上限)`，但现有中间取整和阶段边界应保留。净收入 300，同时存在世界 ×1.20 和手伤 ×0.85，结果是 306；不是把百分比随意相加得到 315。

`work.health_cost` 表示正数消耗量，额外 +2 意味着更加伤身；现金变化、健康变化等最终状态再应用一次。现有世界 `healthChange` 同时放大恢复和损失，新设计可以分为 `health.damage` 与 `health.recovery`，但迁移旧世界事件时必须映射到两边，保持原行为。

工资倍率不会自动乘到罚款、诊所支付或投资本金；投资盈亏、回报上限、报价、卖出收入、利息各有独立统计项。UI 的效果明细应从同一计算器取得来源列表和实际结果。

## 8. 触发效率：先决定何时查，再决定查谁

### 8.1 把时机、资格、抽取分开

| 层次 | 回答的问题 | 例子 |
|---|---|---|
| Hook | 什么时候检查？ | `after_work`、`enter_week`、`after_travel` |
| Condition | 这个状态有没有资格？ | 做后厨工作且没有手伤 |
| Pool policy | 合格内容如何抽取？ | 一次工作最多出现一个意外 |
| Repeat policy | 以前发生过是否还能来？ | 全局一次、阶段一次、冷却 8 周 |

示例 `pool.work_incident`：每次完成工作先检查候选与权重总和；无候选则无事件。有候选时抽一次 20% 的发生概率，成功后再按权重从候选中选一个。某事件权重为 10，不代表它有 10% 概率。

在这个新池中，若合格候选权重分别为 10 和 30，前者发生概率为 `20% × 10/(10+30) = 5%`。概率和权重不能混成同一个 `triggerChance` 字段。

现有地点池保留“按运气选类别 → 类别内抽取 → 空类别回退”；人生选择保留“阶段内一次”；世界事件保留指定周的一次判定。可以给池设置策略枚举，而不是把每个事件的随机分支写回引擎。世界事件初期仍可限制为同一时间一个世界事件，与角色身上的手伤并存。

### 8.2 索引只保存稳定信息

启动时加载和校验内容一次，建立 `ID → 对象`、`hook → 事件`、必要的 `地点 → 事件` 索引。游戏动作发生时，只评估相关候选的动态条件，不在 SwiftUI 重绘或每一帧中遍历整个库。

| 查询 | 合适的实现 |
|---|---|
| 查事件或修正定义 | 字典按 ID 查找 |
| 工作后抽事件 | `after_work` 候选数组，必要时再按工作标签过滤 |
| 进入一周 | 指定周事件 + 周期池 + 到期任务队列 |
| 判断复杂条件 | 对缩小后的候选短路计算 `all/any` |

先使用普通数组、字典和集合，测量候选数量、条件调用次数与动作耗时后再优化。现有线性筛选在当前规模下没有经过性能测量，不能仅凭 56 条事件就判定“已经慢了”。缓存现金/健康等动态判断会引入失效问题，初期不做。

冷却建议从结算周起算：第 10 周结算、间隔 8 周，则第 18 周起再次合格。事件待选期间也要占用该定义与目标的触发资格。日志只供阅读，一次性、冷却、已选事实使用专门状态。

## 9. 每次动作的结算顺序要写清楚

新引擎需要统一时间语义，并保留旧规则的阶段边界。当前 `GameSession.day` 实际代表“周”；内容格式使用 `week`，通过适配读取，避免顺便破坏存档字段。

跨周建议以以下阶段为骨架，迁移时分别核对旅行、原地结周、跳周路径：

1. 保存离开本周时的有效修正，用于结算这一周的利息；检查当前行动是否合法。
2. 推进到下一周，执行现有利息与生活费用结算；检查死亡和第 52 周终局。
3. 按新周移除到期修正，判定新周世界事件，加入新修正。
4. 按动作路径处理市场和地点事件，再检查人生选择及到期故事链。
5. 按既定顺序生成待展示通知/待选事件，保存状态和随机检查点。

特别注意现有差异：`travel` 先抽地点事件，再让市场优先包含该事件商品，最后施加效果；`advanceStationaryWeek` 先生成市场再抽事件。不能在迁移时统一排序而无意改变可售商品和随机数消耗。

主动选择的结算流程：重新检查选项与目标 → 在状态副本上扣除全部代价并执行效果 → 成功后一次提交状态、实例完成标记和随机状态 → 保存 → 展示实际结果。失败时不应留下“钱扣了，增益没加”的半成品。预览不消耗随机数，重复点击同一实例不重复结算。

UI 负责呈现；关闭通知不能再调用效果。当前 Store 已有世界通知和地点通知的排队，后续用有序通知队列承接；选择必须处理完的阻塞规则由引擎执行。

## 10. 后续事件：保存承诺，不立即递归

假设“带伤上工”之后两周可能出现老板慰问，可以在选项中加 `schedule_event`，保存目标事件、到期周、来源实例和绑定地点/工作。到期后进入队列，重新判断约定的条件。

每个延迟任务声明条件失效时的处理：取消并记录原因，或在截止周前重试。这里可约定：若玩家已经离开相关工作关系则取消；若游戏尚未实现雇佣关系，不要凭 `jobID` 假装存在这种关系。

故事链进度必须绑定事实或链实例。`resolvedEventIDs` 只能回答发生过，不能区分“休养”还是“硬撑”；关键选择保存 `eventID + optionID` 或专门事实。同一链允许重复时，使用各自的链实例，避免上一次故事的事实解锁下一次故事。

禁用同步递归触发。跟进事件通过队列运行；同周派生链设置深度和数量上限，超出时保留未处理任务并报告。静态检查引用环只能提示风险：有时间间隔和终止条件的循环可以合法，是否无限还需要运行时防护。

跳过多周也要逐周运行必要结算；遇到阻塞选择时保存尚未推进的周数，选择结束后继续，不能丢掉剩余时间。该部分应单独验证，再迁移现有拘留/跳周故事。

## 11. 存档与随机：读档不能重抽，也不能重复给奖励

建议在现有快照版本之外增加：

```text
saveSchemaVersion       存档结构版本（延续现有 version 的职责）
contentVersion          本局采用的内容包版本
rulesVersion            计算/随机规则版本
randomCheckpoint        已有随机状态
eventRuntime
  pendingInstances      尚待选择的实例及绑定参数
  cooldowns             定义 ID + 目标 → 下次可触发周
  occurrences           次数、最近发生/结算周
  facts                 类型化的故事事实与阶段进度
  scheduledEvents       到期事件、重试/截止规则
  activeModifiers       持续修正实例
```

实例生成、效果执行、随机数推进和完成标记属于同一个快照提交。关闭 App 再打开后恢复同一选择，已经结算的结果只重现文本，不重新发奖。

种子不是全部：内容列表、遍历顺序、条件、权重和随机调用次数变化都可能改变结果。新内容包采用明确且稳定的候选顺序；迁移旧池时保留旧数组顺序或把变化计入规则版本，不能宣称“用了同一种子就跨版本完全重放”。

内容版本号本身不能恢复旧内容。发布策略必须二选一：保留受支持的旧内容包，或编写显式迁移。初期可采用后者：保留旧 ID，迁移活动实例和待选项，为删改对象提供映射；历史结果保留实际值。修正改版时要明确活动中的旧修正沿用旧值还是升级，建议本局活动实例冻结旧强度，新触发实例使用新定义。

无法恢复的待选对象应给出可记录、可恢复的兼容处理，不能默认把玩家存档清空。迁移测试覆盖当前 v2 快照、待选人生事件、活动世界事件、旧声望字段，以及迁移前后读取两次的幂等性。

## 12. 校验与调试比文件夹数量更影响开发效率

以下为计划实现的工具能力，目前没有这些命令：

| 工具 | 解决的问题 |
|---|---|
| `validate-content` | 结构、类型、ID、引用、数值、图片和文本错误 |
| `export-event-catalog` | 从内容生成唯一的策划总表 |
| `explain-event <id> --fixture <name>` | 为什么某个状态触发不了这个事件 |
| `trace-modifiers --fixture <name>` | 工资为什么从 300 变成 306，每项来自哪里 |
| `find-references <id>` | 改共享规则时，哪些事件会受影响 |

最低限度检查：

- 重复对象 ID、重复 JSON Key、空或非法选项 ID、未知操作码；JSON Schema 不能独自检查所有重复 ID 与跨文件引用。
- 引用不存在的条件、效果、修正、地点、工作标签、图片或文本；共享规则循环引用。
- 概率在 0～1、权重非负且合格池权重总和大于零、持续周数合法、倍率和统计项适配。
- 选择事件至少有一个保证可用的兜底，或者有明确取消处理。简单静态矛盾可发现，任意条件“永远为假”不能承诺由普通 Schema 证明。
- 本地化占位符匹配，图片资源确实进入 App Bundle，内容文件被 Xcode 正确打包。

开发期报告应带文件、对象 ID、字段路径和原因，例如：

```text
events/work/kitchen-injury.json
event.work.kitchen_injury → options[0].effects[1].id
引用的 modifier.health.recovering_hand 不存在
```

解释器应能给出这样的调试结果：

```text
后厨受伤 / 第 10 周 / after_work
✓ 周次 ≥ 8
✓ 本次工作有 kitchen 标签
✗ 已有 手伤未愈，直到第 13 周
结论：不进入候选池，因此没有抽随机数
```

规则测试优先覆盖：钱刚好够/差 1、健康归零、所有选项不可用、修正重叠与到期边界、重复点击、读档恢复、延迟目标失效、世界事件与地点事件同周发生、跳周中断、终局取消任务。内容增多后，再用固定种子批量模拟抽取覆盖率和事件频次；这能发现疑似不可达内容，不能证明所有可能状态都正确。

## 13. 分阶段迁移与完成标准

| 阶段 | 具体工作 | 完成标准 |
|---|---|---|
| A：稳定内容入口 | 固定现有 ID/选项含义；JSON 模型、加载器、最低校验；先迁 3 条代表事件 | 同一内容只在一处维护，错误引用能被发现 |
| B：通用条件和效果 | 现金/健康/运气、商品报价/赠送、布尔组合、代价、实际结果记录 | 旧效果保留取整、容量和边界规则；新增组合无需改引擎 |
| C：持续修正 | 活动实例、来源、时长、重复策略；接入世界事件和装备计算阶段 | 世界事件、工具、手伤可同时作用，移除后数值正确 |
| D：调度与故事链 | 池策略、阶段一次、冷却、待选实例、延迟队列、存档迁移 | 读档无重抽/重复奖励；各路径按既定周次结算 |
| E：全量迁移与作者工具 | 迁移其余事件，生成总表，加入条件/修正解释工具 | 普通事件开发主要发生在内容文件里 |

三条试迁内容建议选：`san-gabriel-kitchen-burn`（健康）、`studio-camera-rush`（报价）、`community-leftovers`（受容量限制的赠品）。先通过旧引擎适配器执行新定义，保留现有内容 ID、池顺序、数值与资源名；同一事件不能同时注册新旧两份。

之后迁 `labor-enforcement-wave`，验证世界修正接入；再迁一条人生选择，验证实例、选项身份和读档。本文新的“后厨受伤选择”作为能力演示，应在这些旧行为通过验证后加入。

每阶段都使用现有 `GameEngineTests` 加有针对性的兼容用例，比较固定种子和动作序列下的现金、债务、健康、运气、市场、活动修正与随机检查点。确实要调整玩法时单独记录规则版本和预期差异，避免把平衡变化藏进结构迁移。

模组覆盖、远程内容、热重载和可视化节点编辑器可以后置。当前重复 ID 一律报错，内容包随 App 发布。共享条件/效果只有出现实际复用时才提取。

## 14. 用这三个问题练习读事件文件

1. 把“只有健康低于 40 且没有住房时，才可能遇到免费诊所”写成一棵条件树。再指出应该在哪个动作后检查，而不是每帧检查。
2. “获得 $100”和“未来 3 周工资提高 10%”分别属于什么？存档应分别记录哪些信息？
3. 玩家支付 $80 的选项在弹窗时可用，点击时余额却不足，应由哪一层拒绝？关闭再打开弹窗后，为什么不能重新抽结果？

参考答案：第一题是 `all(health < 40, not(hasHousing))`，可放进明确的地点/周事件池；第二题分别是一次性效果和持续修正，前者保存实际结果，后者还保存活动实例和到期边界；第三题由引擎重新校验并原子结算，事件实例保存随机结果与完成状态。
